# onHold

React + Rust (Axum/PostgreSQL/Redis) + BNB testnet contracts. Homepage has one website card; Claim, Analytics, Burn and Docs have separate routes. The interface defaults to English and offers English, Chinese, Japanese, Korean, Spanish, French, German and Portuguese. Some advanced error/setup and tutorial copy still falls back to English outside English/Chinese.

The sidebar and liquid indicator, mobile navigation, wallet button, Claim feed, and animated homepage analytics use the actual SingleSpark components. The homepage offers 1H / 4H / 7D / 30D controls over recorded financial history. Digits and recorded curves loop their visual animation even at zero without changing the displayed totals. Configured Burn totals are checked and persisted every 3 minutes; homepage history refreshes every 15 minutes.

The UI uses the actual local SingleSpark component-atlas distribution, copied into `front/components/singlespark` with its source reference, plus its adapted TokenMediaUpload. Nunito is served locally under its OFL license. The supplied colorful $OnHold artwork is used unchanged.

## Project structure

- `front/`: the only frontend project. `src/main.jsx` mounts the app; `components/onhold/` contains all business React components and `components/singlespark/` contains the required shared component library; `src/` contains business logic and assets, `test/` contains frontend tests, and `dist/` is generated by the build. Do not edit `dist/` directly.
- `backend/`: Rust API, SQL schema, runtime/keeper scripts, integration tests and ignored persistent `data/`.
  Database locations, table purposes and inspection commands: [backend/sql/README.md](backend/sql/README.md).
- `contracts/`: Solidity source, pinned upstream code and licenses, compilation/deployment scripts, contract tests and public deployment records. `artifacts/` is generated by compilation.
- Root `package.json` and `package-lock.json`: shared npm workspace installation and commands. Run `npm ci` once at the project root.

From the project root, run `npm run build`, `npm test`, `npm run dev`, or `npm run start:testnet`. For frontend-only work, `cd front` then `npm run build`, `npm test`, or `npm run preview`. The static preview listens on port 4189; API-backed pages use port 4190. React pages use `/`, `/claim`, `/analytics`, `/burn`, and `/docs`, with one generated `index.html` entry. Old page URLs ending in `.html` are unsupported; invitation links use `/claim?ref=…`. The mint page no longer embeds the public NFT gallery. Mining shows the current wallet’s staked NFT cards; Add stake selects from its unstaked NFTs, and each staked card has an individual Unstake action. Both lists use wallet-scoped PostgreSQL pagination (12 cards per page), so they are not limited to the first 50 NFTs. Generated build output is ignored by Git. Never delete `backend/data/` as a cleanup step: it holds databases, testnet keys and recovery journals.

## Docker images and Rainbond

Build from the repository root for `linux/amd64`. The `api` image contains the Rust server and compiled frontend; the `keeper` image runs the separate scheduled executor. The Rust build cross-compiles from the builder's native architecture. Other target architectures are currently rejected explicitly.

```sh
docker buildx build --platform linux/amd64 --target api --tag onhold:api --load .
docker buildx build --platform linux/amd64 --target keeper --tag onhold:keeper --load .
```

`.dockerignore` uses an allowlist: private `backend/data/`, local environments, Git history, host dependencies and generated output are excluded from the build context. Only compiled frontend files and the API binary enter the API runtime; the keeper contains its two scripts, public ABI/policy and production npm dependencies. No wallet keys or local databases are copied. Inject secrets at runtime, never through build arguments. The generated mainnet wallet backup is not a deployment configuration file.

`rainbond.app.json` defines the website/API, an independent PostgreSQL database and Redis cache. Business images use separate `onhold-...-api` and `onhold-...-keeper` tags in the existing ACR repository `registry.cn-hangzhou.aliyuncs.com/xmhxiansheng/singlespark`; middleware uses the Docker Hub mirror `docker.1ms.run`. Configure private-registry pull credentials at runtime. Keep the API at one replica for its SQLite-backed authorization flow. Add the separate keeper component only after a real Flap market is ready, also at one replica.

The local Rainbond binding and runtime secrets are under Git-ignored `.rainbond/`; the secrets file has mode `0600`. PostgreSQL has a separate application login with schema permissions, while its administrator credential stays on the database component. Each component has its own persistent data directory. Back up the secret file and database data privately.

## Advertising

The entire homepage card opens its HTTPS website. The form accepts avatar upload, official URL, an 80-character description, selected/custom feature tags with **up to 10 tags, each with up to 10 Unicode code points**, and a bid. No site name or backend technology field is shown. Previous records are retained; only slot 0 is offered in this UI.

The contract requires at least **0.001 BNB** and at least the current price plus 10%, rounded up to wei. Price stays unchanged for the first 24 hours, halves every complete 24 hours, and bottoms at one wei. A replacement resets the clock. Ad fees are paid in full, without a refund to the previous advertiser; every paid bid splits into a team balance (floor of 50%) and a protected buyback reserve (the other 50%, including any odd wei). The owner can withdraw only the team balance. Version checks reject stale listings. Ad revenue is separate from token creator fees.

`POST /api/uploads/avatar` accepts PNG/JPEG/WebP up to 5 MB and reuses SingleSpark’s Pons/IPFS upload protocol: fixed `https://ponsfamily.com/api/ipfs/image`, multipart `image`, canonical CID and matching `ipfs://` URI validation. No browser cookies or server credentials are forwarded. Public images use the Pinata gateway. R2 and Cloudflare Images are not used. Failed/redirected/oversized upstream responses fail explicitly; two concurrent uploads are allowed. Pons pin retention is not guaranteed; retain originals for repinning. Production should replace the global upload quota with wallet-bound upload tickets before opening high-volume public traffic.

## Restricted-account NFTs and staking

The NFT contract inherits a fork of **Synthetix StakingRewards from the fixed official `synthetix@2.27.2` package**. The original source, MIT license, package integrity, source hash and adaptation diff are retained in [`contracts/staking/SOURCE.md`](contracts/staking/SOURCE.md). Its original reward-per-token ledger, earned calculation, updateReward checkpointing and getReward pull payment are reused. NFT custody, weighted stake balances and the fixed 365-day linear release schedule adapt that implementation. The former custom reward ledger is removed; there is only one source of reward accounting. `getReward()` is the client claim entry point. The adapter uses the installed OpenZeppelin 5.4 NFT and safety primitives. Modified contracts are not covered by any upstream audit.

The former wallet-binding / one-time token compensation flow is removed. `POST /api/verify` accepts a sessionKey in the body, calls only `https://claude.ai/api/account/standing`, and discards the credential. Redirects are disabled; no arbitrary cURL or URL is executed. It requires bad standing, no active organization, one consumer organization UUID and a prior plan of `free` / `claude_free`, or containing exactly one of `pro` or `max` (case-insensitive). API organization entries are excluded when selecting the consumer UUID; multiple consumer candidates are rejected. HTTP errors and CAPTCHA are not treated as bans. This internal endpoint can change. On 2026-10-20, the cloud Claim page successfully verified a real restricted Max account and generated its browser PNG preview with weight 3; real-account minting, staking and claiming were not completed in that run.

The consumer organization UUID is hashed for deduplication. It is **not a personal user ID or proof of a unique human**. The previous plan is not a current subscription. No full billing or ban history is available. The browser shows the verified plan, UTC restriction time, linked organization name, category and NFT weight. With explicit user consent, the full organization name, raw UUID, exact ban timestamp and previous plan are signed, stored once in contract storage, and exposed by a fully on-chain Base64 tokenURI. There is no metadata setter. The wallet authorization states permanent public disclosure and includes the exact fields. Short-lived verification metadata is stored against the 10-minute verification token and expired on later verification. `prev_plan_tier` is the previous plan, not a subscription date; no start/expiry dates are inferred. Free passes can mint with weight **0** and earn no mining rewards; Pro passes have base weight **1**, Max passes **3**. Holding earns nothing; **staking is mandatory**. NFTs can transfer; staked NFTs are escrowed and only the original staker can withdraw. Accrued rewards remain claimable after unstaking.

`/api/nft/quote`, `/authorize` and `/receipt` implement wallet consent, EIP-712 **MintPass v5** signing, reservation and confirmed-mint recording. Proofs bind recipient, organization nullifier, tier, referrer, deadline, chain ID and contract. Each verified organization UUID can mint only once. One wallet may mint many distinct organizations and stake multiple NFTs. A wallet’s first mint or first stake permanently locks its single inviter (including no inviter). Receipts require the configured contract, matching PassMinted event and three confirmations. Public transaction hashes can retry synchronization without credentials. The old `claims` table is preserved as legacy history; new reservations and token IDs live in `nft_mints`. Old proof versions cannot mint or claim.

The initial combined mining and referral budget is **100,000,000 $OnHold**, funded before the first stake. `BASE_MINING_POOL = floor(100m ×100/115)` is approximately **86.9565m**; the remaining approximately **13.0435m** is reserved for the inviter’s additional 15%. The first funded stake starts a fixed 365-day window. Base rewards release uniformly by block timestamp at approximately 238,237.05 tokens per day initially (base budget / 365), without weekly halvings. Advertising buybacks can increase the funded budget and future release rate as described below. The cumulative schedule is capped at the funded base budget; new accrual stops at the end, while earned and referral rewards remain claimable. Claiming does not unstake NFTs or reset the clock. Including the maximum additional 15% referral accrual, the daily-equivalent allocation is approximately 273,972.60 tokens. Actual claims and sales may be delayed or concentrated, so these rates are not daily selling limits. It does not depend on an assumed BNB block interval or a server scheduler. Pro and Max weights stay exactly 1 and 3. An interval without any stakes distributes nothing; rounding and unallocated reserves remain in the pool, with no owner withdrawal.

Invitation links use a persistent **12-character short code** (`/claim?ref=a7c29d4e8f31`), not an exposed wallet in the query. `POST /api/invites` validates a public wallet and returns its stable SQLite code; it does not establish wallet ownership. The backend resolves the code for minting and rejects self-referrals and unknown codes. Legacy address links are converted to short codes. Preserve the SQLite database when deploying so existing links keep working.

When an invited wallet calls `getReward()`, it receives its entire base mining amount. The contract accrues **an additional 15% of that actual amount to the inviter** in `referralRewards`; the inviter calls `claimReferralRewards()` to receive it, without needing to own or stake an NFT. For example, 10,000 base tokens + 1,500 referral tokens = 11,500 total tokens spent. It is a single-level reward on base mining only, never on referral payouts. Sub-wei fractions carry across claims, so splitting claims does not change the total bonus. Multiple NFTs share the wallet’s inviter. NFT mint recipient and original inviter are also recorded in `mintedFor` and `passReferrer`. Transferred NFTs mine according to the current staking wallet’s locked referral relationship; transfer does not reassign a wallet’s inviter.

Configure `ONHOLD_MARKET_ADDRESS` and a dedicated `ONHOLD_VERIFIER_PRIVATE_KEY`, and set that key's public address as the contract verifier using the owner wallet. Both client and backend require `onhold.nft-staking.v4` / API `nft-staking-v4`; all older deployments, including v3 weekly-halving contracts, are rejected and need a fresh deployment. Existing contracts are immutable; changing sources does not change their schedule or migrate NFTs, rewards or funds. Existing deployment manifests are retained as history; use a separate test data directory and update runtime addresses only after a new deployment is verified. The verifier is trusted to attest restrictions; this is not a trustless provider oracle. Do not use a funded personal wallet as this signer. Reward tokens must use 18 decimals with standard, non-rebasing transfer behavior; production Flap tax behavior needs validation before funding.

The Claim guide explains F12 → Network → F5 → standing → right-click → Copy → Copy as cURL, including Mac shortcuts. Its real user-provided Network screenshot has numbered SVG callouts in both the thumbnail and enlarged view. The next step shows how to paste the cURL in the real empty form. The English restricted-page capture uses Chrome Translate; no verification outcome is fabricated. Source details are in `front/src/assets/guide/SOURCE.md`.

## Advertising buyback and mining replenishment

The market automatically accounts for 50% of each advertising payment as `teamRevenue` and 50% as `adBuybackReserve`. `withdrawRevenue` cannot access the reserved share. Advertising fees are distinct from Flap trading-tax revenue: ad fees buy tokens back into mining; trading taxes continue to buy and burn. The same tokens are never both burned and distributed.

`reinvestAdRevenue(amount,minOutput,deadline)` lets the configured `adKeeper` spend only the advertising reserve through the chain's pinned Flap Portal, with a positive minimum received amount, a deadline no more than two minutes away, a minimum of 0.001 BNB on testnet/local (0.01 BNB on mainnet), and at least three minutes between executions. It measures the actual token balance increase, so only tokens really received are funded. Swap failures, insufficient output or failed funding revert the entire transaction; refunds remain in the ad reserve. The team balance cannot be spent by this function. Gas is funded separately by the ad keeper, with no deduction from the 50% advertising reserve.

Purchased tokens are divided into base mining (`floor(received × 100/115)`) and the additional 15% referral reserve. Before changing the release rate, the contract checkpoints the old schedule so existing earnings do not change retroactively. Remaining base rewards plus newly added base rewards release uniformly over the **remaining original 365-day window**. Top-ups never move the end date. The displayed funded pool and daily base emission therefore increase after purchases. Historical schedule queries use stored emission segments. No-stake intervals are skipped; they do not extend the window or redistribute missed rewards. Buys wait until mining starts and stop at expiry; unspent BNB remains reserved. Late top-ups have a shorter release window and can materially increase the final days' daily-equivalent rate. A new period after expiry is not implemented.

Run `npm run keeper:ads` with `ONHOLD_AD_REINVEST_MARKET`, `ONHOLD_KEEPER_PRIVATE_KEY`, `ONHOLD_KEEPER_MAX_GAS_PRICE_GWEI` and the existing slippage/data-dir settings. The owner sets the worker wallet with `setAdKeeper(address)` and funds its gas. This worker reuses the existing signed-transaction journal and recovery process; a wallet-level lock prevents two keeper processes from signing concurrently with the same wallet. Use separate wallets for simultaneous trading-tax burn and ad-reinvestment workers. The executable remains restricted to BNB testnet; no production automation is activated by these source changes. A live Flap market and Portal route must exist; the standalone test token cannot be traded through the real Portal.

## Flap buyback and burn

`FlapBuybackFactory` accepts native BNB, buy/sell tax of 300 bps each, and 10,000 bps to the vault, rejecting other allocations. It implements Flap’s supported v2.2 factory surface; the vault inherits the pinned official VaultBaseV3. The same vault/factory source deploys on BNB mainnet (56), testnet (97), and local development (31337), rejecting other chains. The factory selects the corresponding official VaultPortal by chain ID; local tests use the testnet identity. The factory is supplied to Flap VaultPortal during launch, which creates the vault for the predicted token address. This is separate from the standalone test-token setup button. `ClaudeTestToken`, `TestDeployment` and `deploy:testnet` remain test-only; production must use the actual launched token, not test tokens.

`FlapBuyback` recognizes incoming native fees by balance delta, keeps receive() lightweight and spends only via the pinned Flap Portal to buy its immutable token. Purchased tokens are transferred to `0x000000000000000000000000000000000000dEaD`. This removes them from circulation; it does not call an ERC20 burn method or reduce the token’s reported totalSupply. There is no arbitrary withdrawal. The keeper and irrevocable Flap Guardian can execute, with a positive minimum output, short deadline and at least 180 seconds between successful buys. Failed swaps revert accounting atomically. The minimum is 0.001 BNB on testnet/local and 0.01 BNB on mainnet. `settleAndExecute()` calls the token-bound Flap TaxProcessor `dispatch()` directly into this vault, then buys and burns in the same transaction. Below the threshold, the keeper skips the cycle. Every successful keeper execution reserves at most 0.0001 BNB and reimburses measured in-contract gas (including settlement) up to that cap. Intrinsic transaction gas and the final refund transfer are excluded; this is partial compensation, not an exact receipt refund. The rest of the reserve stays in the vault. `totalSpent` counts purchases only; `totalGasRefunded` is separate. Therefore the policy is **100% of fees after gas compensation**, rather than 100% of gross fees. The keeper needs startup gas and cannot be kept funded when fee income stops. Fees still waiting in a Flap splitter/processor are not counted as received vault revenue. This contract change does not switch the frontend, API or keeper to mainnet; their current runtime/deployment flows remain configured for testnet.

After deploying a real testnet Flap token/vault, run the separate Node/ethers executor with `npm run keeper`. Configure `ONHOLD_BUYBACK_VAULT`, `ONHOLD_KEEPER_PRIVATE_KEY`, and `ONHOLD_KEEPER_MAX_GAS_PRICE_GWEI`. Slippage defaults to 100 bps and may be set with `ONHOLD_KEEPER_SLIPPAGE_BPS` (1–500). The keeper verifies the processor’s token, native quote and direct vault beneficiary, plus the on-chain minimum/refund cap. It quotes the combined vault balance and pending creator fees less the gas reserve, and schedules one eligible attempt every 180 seconds. Fund the dedicated keeper with test BNB for gas. Its local signed-transaction journal is fsynced before broadcast and resent unchanged after a restart; a lock prevents concurrent workers. After an unclean process death, verify that no worker is running before removing the stale lock. Pending transactions that remain stuck require operator intervention. No live swap has been performed or independently audited.

For Rust read-only indexing configure `DATABASE_URL`, `ONHOLD_BUYBACK_VAULT` and `ONHOLD_BUYBACK_FROM_BLOCK` (vault deployment block). Set `ONHOLD_BUYBACK_FLAP_LIVE=false` only for the standalone test ERC20; its absent Flap balance is shown as unavailable rather than fabricated. `/api/burn` reads PostgreSQL only, using a repeatable-read snapshot of `buyback_state` and `buyback_events`; page refreshes never trigger RPC. Every 180 seconds the Rust worker reads the confirmed vault balance and Flap TaxProcessor `marketQuoteBalance()`, persists accumulating/cooldown/eligible status and check time even below threshold, while the shared WS stream applies confirmed revenue, burn and gas-refund events directly. HTTP log reads occur only at startup, reconnect or recovery. Failed RPC attempts preserve the last confirmed totals and cursor; the API keeps this DB snapshot available and marks it stale until synchronization recovers. The API returns contract totals, gas compensation, actual native vault balance, pending Flap creator fees, policy thresholds and the latest 100 indexed buyback events. The Burn page has Overview and one combined Buyback & burn history. Each confirmed transaction uses the existing SingleSpark `BurnCard` (including its expandable detail and BNB → $OnHold → burn route), with the supplied backend data rather than the atlas’s captured preview records. It displays the threshold, accumulating/cooldown/eligible state, gas cap and total compensation alongside burn totals. The indexer catches up in 1,000-block batches and excludes the newest three blocks. The live stream checks header ancestry and log block hashes; reconnect verifies the saved hash. A detected reorganization rebuilds the affected projection from its deployment block. Cursor, event rows and totals commit together, with unique vault/transaction/log keys. Old SQLite files remain intact; chain history is rebuilt from logs. Confirmed transactions normally appear within the three-block safety lag plus the one-second commit interval. If indexing is down, restart catches up from the stored cursor. Missing configuration displays deployment pending, not fake zero-valued financial totals. The site being open does not itself schedule transactions; the keeper must run continuously. Insufficient funds, a failed quote or a gas ceiling postpones execution.

Flap’s bonding-curve fee is an additional 1% on top of the selected 3% token tax. Current documented BNB curve parameters are illustrative; read actual immutable token parameters and quote the Portal before any purchase. At total supply 1 billion, buying the first 30% on the documented r=6.14/h=107,036,752 curve costs approximately 2.282424 BNB net, or 2.377525 BNB gross at a 4% input fee, excluding creation and gas. This is an estimate, not a fixed offer or an executed purchase.

## Telemetry, deployment limits

Rust records page views, ad clicks and wallet connection events with random event IDs and server timestamps. Event IDs are idempotent; browser origin and field validation are enforced. Existing SQLite telemetry is migrated without discarding records. Clicks are public client telemetry, not fraud-resistant billable traffic. Ad UV counts distinct server-observed IPs per campaign (contract + slot + version), cumulatively for that placement. Repeated clicks from one IP increase clicks but count once in UV; different users behind one shared IP also count once. IPs are normalized and stored only as keyed hashes using a stable database-held random salt; raw IPs are not retained or returned. Legacy events without an IP hash retain their clicks and contribute no UV. The server aggregates all telemetry once at startup, then every 15 minutes into an immutable in-memory snapshot; `/api/stats` and campaign clicks/UV in `/api/chain` read this snapshot without scanning events. `updated_at` identifies the aggregation time. Failed refreshes retain the previous snapshot. For reverse proxies, configure `ONHOLD_TRUSTED_PROXIES` as a comma-separated list of exact proxy IP addresses and have the proxy overwrite or append `X-Forwarded-For` correctly. Forwarded IPs from other peers are ignored. New chain campaigns attach contract, slot and version to click events. Cached current and historical ads use these campaign counts; legacy slot-only events are not fabricated into historical campaign counts. History shows paid bid and actual display duration, with the latest 200 ended campaigns displayed.

No Claude credential is logged or stored in SQLite, browser storage or chain. The server stores verification hashes, NFT reservations, invite-code mappings and mint wallets to prevent duplicate mints. Retention and operational controls must be set before production scale.

Local unit/integration tests cover contract rules, linear-release start/end boundaries, invitee bonuses, proof replay, buyback accounting/reverts, quote validation and telemetry persistence. Pons upload/readback and public BNB testnet deployment were verified on 2026-10-20. Live Claude verification and browser PNG preview passed on the cloud Claim page on 2026-10-20. The full real-account mint/stake/claim flow and live Flap swaps still require end-to-end testing. Contracts have not had an independent security audit. The private Sites preview hosts static frontend only; Rust and the keeper require their own runtime. Source synchronization to that external host was blocked by automatic approval review, so the hosted preview is not the current local version.

## Wallet interaction timing and global rewards

After connection, every page shows the estimated mining reward and claim action in the sticky top bar. It reads the existing wallet-specific backend snapshot every 15 seconds, refreshes on page visibility and completed mining actions, and makes no RPC calls merely to display that number. Wallet snapshots continue to bypass the shared public cache. The contract determines the settled payout.

Connection, invitation binding, signing, gas estimation, wallet confirmation, chain/index confirmation and balance refresh show separate elapsed times in the existing interaction dialogs. Wallet prompt durations include user confirmation time; backend durations include network transit; mining confirmation includes the indexer and its existing 2-second polling interval. Durations stay in memory, freeze when an attempt ends, and contain no addresses, signatures, messages or transaction payloads. Reload recovery measures the recovery attempt, without inventing missing historical timings.

Account and chain checks run in parallel, retaining checks before sends. A stake reuses its signer after NFT approval and still rechecks the selected wallet. The global claim control and staking page share a submission guard to prevent simultaneous duplicate preparations. No network, confirmation depth, referral binding or approval scope was changed.

## Public first-screen cache

The root HTML embeds the three public home reads (stats, the configured market snapshot, and 30-day mining history). `GET /api/home` refreshes the same bundle. Public GET responses use a 5-second memory cache and may serve the previous response for another 10 seconds while one background task refreshes it. Cold bursts wait on that same task. Failed refreshes do not overwrite a successful snapshot; after 15 seconds an expired snapshot is no longer served. Confirmed source snapshots keep their original `stale` and block metadata when indexing is catching up; cache age does not imply source freshness.

The browser reuses only this public bundle, including session navigation, with the same 5/15-second limits. Wallet queries, authorization/cookie-bearing requests, writes, unknown queries, and other markets bypass the public response cache. Transaction follow-up reads force a fresh fetch; successful NFT authorization/receipt writes invalidate cached snapshots. `X-Response-Cache`, `Age`, and `Server-Timing: app` expose cache behavior and backend duration. HTML exposes `Server-Timing: home`.

## WebSocket → PostgreSQL → API, with Redis metadata cache

Configure `ONHOLD_MARKET_ADDRESS`, the exact `ONHOLD_MARKET_FROM_BLOCK`, and `ONHOLD_CHAIN_WS_URL` (BNB testnet WSS). `ONHOLD_CHAIN_RPC_URL` optionally supplies the corresponding HTTP endpoint. Read-only indexing does not require a verifier private key. Rust uses one shared WS connection with two subscriptions: `newHeads` and logs filtered to the configured market and buyback vault. WS log payloads drive both projections directly. Headers and logs are buffered until head minus three, validated for ancestry and matching block hashes, deduplicated by block/log index, and committed to PostgreSQL at most once a second. In-memory pending data is bounded; overflow, missing heads, removed logs or conflicting hashes trigger reconnect and cursor recovery. A late previously unseen confirmed log forces replay rather than being discarded. Startup/reconnect checks chain ID on both transports, market protocol and the canonical constructor ownership event at the exact deployment block (without requiring pruned historical world state), validates the saved checkpoint, and backfills in 1,000-block batches. An initial unconfirmed overlap read closes the subscription/backfill race. Normal live operation does not poll block numbers or logs over HTTP. Derived PG rows, raw market events and each index cursor commit atomically. Confirmed DB snapshots remain available during disconnects and catch-up, with `stale`, `connected`, `syncing` and the checkpoint timestamp reported separately. Only a projection without a confirmed DB checkpoint is unavailable; readiness still requires a healthy live indexer; `last_error` reports a safe diagnostic code (including `protocol_mismatch`) rather than hiding all failures as WS disconnects.

`GET /api/chain?market=0x…&wallet=0x…` reads PostgreSQL on every request, for the staking ledger and ownership; campaign clicks and UV come from the 15-minute analytics snapshot. A repeatable-read transaction keeps each reward estimate consistent with its indexed block. Redis caches only immutable NFT account metadata and SVG images by content hash, with a 24-hour TTL; missing entries are loaded from PG. Redis failure falls back to PG and briefly suppresses further cache attempts. It never determines payouts. It makes **zero RPC requests per API call**. The frontend no longer polls RPC for advertising or NFT mining. The replay uses on-chain `RewardsCheckpoint` events from the existing StakingRewards ledger, including zero-reward updates, so rounding follows contract checkpointing. Estimated pending rewards use the latest indexed block timestamp, not server time. Wallet transactions always settle using the actual chain state.

Configure `DATABASE_URL` and optionally `REDIS_URL` alongside the chain provider. The schema in `backend/sql/chain.sql` creates separate chain state, wallet, NFT, ad, raw event, payee and analytics tables with ownership/staking indices. The API uses a bounded PostgreSQL connection pool. Existing SQLite telemetry is copied idempotently into PG; SQLite is retained for legacy records, short codes and mint-verification operations. Existing files are not deleted. A chain indexer without PG configuration fails explicitly instead of silently serving memory.

Normal live market indexing uses **zero scheduled HTTP RPC calls**; a new NFT still reads `tokenURI` once for its immutable SVG. Burn totals, income, executions and refunds come from WS events. Every 180 seconds Burn retains the required actual vault balance/accounted balance and external Flap pending-fee/beneficiary checks (also immediately after a confirmed Flap buyback, so settled fees are not double counted); these are chain validations, not log polling. Standalone test-token mode performs two balance/accounting calls per check; live Flap mode additionally validates and reads its processor. Mint authorization, transaction recovery and keeper execution retain their necessary direct checks. Bootstrap, reorg recovery and reconnect add RPC backfill traffic. Provider subscription notifications may be billed separately. PG page reads never multiply RPC traffic.

The immutable NFT card uses the actual SingleSpark `CollectibleCard` component. Docs reuses SingleSparkFront’s `OutlineCurve.tsx` and relevant `how.css` rules, with the scroll viewport adapted to `.app-body`; gameplay copy is specific to this project.


## NFT image before mint

Verification parses a live Claude standing response and stores the trusted account record with a short-lived verification credential. The backend returns the account, UUID, ban time and plan without rendering any image or calling `previewPass`. The browser draws an 840 × 924 PNG using Canvas and the locally served Nunito font; this uses the user’s CPU. The layout mirrors `BanPassRenderer` (terminal mascot, ban stamp, record fields and Free/Pro/Max weight). Step 1 places the website button and cURL form on the left, with the Chrome screenshot guide on the right. Next verifies and draws the PNG, then changes to step 2, where the right-hand original SingleSpark CollectibleCard previews the local PNG before upload.

In wizard step 2, after the user connects a wallet and submits, the browser sends one multipart form to `POST /api/nft/create` containing **`verification_token`, `wallet`, optional short `referral_code`, and `file`**. No upload happens during verification/preview. The backend rejects extra record/plan/weight fields, checks a live verification, validates PNG dimensions and pixel decoding with bounded memory/concurrency, and uploads through Pons/IPFS. The saved URL is scoped to the verification session and cannot overwrite a previous completed upload. Failed uploads can be retried without submitting the Claude credential again while the verification remains valid. The next wizard step requires a locally generated PNG; the backend requires the saved image before issuing a mint quote/proof. The form response includes the wallet authorization quote. The original SingleSpark TransactionProgressDialog tracks upload, wallet signature, backend authorization, wallet mint approval and three chain confirmations. Broadcast hashes survive refresh; recovery checks the existing receipt instead of submitting another mint.

Account facts and mint weight come from the stored verified record, never from image pixels or client form fields. After reviewing the PNG, the user signs the wallet authorization and sends the mint transaction. The contract continues to generate its permanent on-chain SVG and metadata from the immutable signed record; the uploaded PNG is a display/share copy, not the source of NFT rights. Browser font fallback and rendering can produce small visual differences from the on-chain SVG. No login credential or CAPTCHA field is included in artwork or uploads.

Copied cURL/Cookie text is parsed locally without shell execution; only one unambiguous sessionKey is sent to `/api/verify`. The full copied request is never forwarded or persisted. The public account-image disclosure appears before verification. Ordinary websites cannot read another origin’s logged-in session; automatic cross-origin session extraction is not implemented.

The indexer fetches `tokenURI` once per new NFT and stores its SVG in PostgreSQL alongside the immutable record. Normal refreshes still make zero RPC requests. Pre-mint Canvas drawing requires no rendering RPC. PNG upload results are saved on the verification session; repeating a completed upload returns its saved URL. The legacy server-rendered `nft_artwork` cache is preserved but no longer used by this flow.

`GET /api/nfts?tier=all|pro|max&page=1&page_size=12` reads the confirmed NFT rows directly from PostgreSQL, newest first. A repeatable-read count and page query stay consistent. Page size is capped at 24; out-of-range pages clamp to the last page after reorgs. Claim shows the original SingleSpark CollectibleCard grid and SingleSpark pagination, with All/Pro/Max filters. There is no RPC per gallery query.

Card timestamps display `YYYY-MM-dd HH:mm:ss` with a UTC label; original full-precision ISO timestamps remain in contract storage and metadata. The default mascot and SVG header use a terminal-style pixel character rather than the CC block.

## Dedicated BNB testnet deployment

`npm run deploy:testnet` generates dedicated local test keys (only if absent), checks chain ID 97 and the gas balance, then deploys TestDeployment (test token + market/NFT staking + immutable SVG renderer), installs a separate NFT verifier, and deploys the buyback factory and a standalone buyback vault for the test token. It never signs for mainnet. The test deployer is also the test keeper. Production roles must be separated. The standalone test ERC20 is not a launched Flap tax token and has no Flap market; deploying this vault does not prove live swaps or creator-fee collection. Its deployment manifest explicitly records `flapLive: false`.

Keys and signed transaction recovery journals are stored with mode 600 under ignored `backend/data/testnet/`. Back up these local test keys privately; never commit or share them, and do not fund this test-only address on mainnet. A public `contracts/deployments/bnb-testnet.json` is written only after receipt/code/funding/verifier checks pass. `front/src/chain-config.json` is then updated to the confirmed market. Rebuild the frontend afterward. `node contracts/scripts/deploy-testnet.mjs --status` checks balance and estimates the core deployment without broadcasting. `ONHOLD_TESTNET_RPC_URL` can select a corresponding HTTPS testnet provider; local integration tests use an isolated `ONHOLD_TESTNET_DATA_DIR`.

Each signed transaction is saved before broadcast; reruns recover the exact transaction and retain deployed addresses. A failed transaction or changed artifact/constructor binding stops rather than silently replacing a deployment. The script reserves 25% gas and refuses gas prices over 5 gwei. Backend verifier, confirmed deployment blocks, PG/Redis and WebSocket provider configuration still need to be installed into the runtime after deployment; private keys are never written into frontend configuration.

`npm run start:testnet` starts the local testnet API using the active public deployment manifest (`contracts/deployments/bnb-testnet.json`, shared with the frontend) and the private verifier key in `backend/data/testnet/keys.json`, with project-owned PostgreSQL and Redis accessed through private Unix sockets. No DB TCP listener is opened. The persistent development data remains under ignored `backend/data/testnet/`; the existing SQLite records are preserved. This requires the already-installed PostgreSQL/Redis executables and a built Rust binary. Its default public HTTPS/WSS provider is `bsc-testnet-rpc.publicnode.com`; production should use a dedicated provider and managed runtime. It does not start the buyback keeper against the standalone test ERC20. To replace an empty obsolete test buyback vault after a contract revision, run `node contracts/scripts/deploy-testnet.mjs --upgrade-buyback` after compiling. This keeps the market, token and verifier, preserves old vault addresses in the manifest, and refuses to replace a funded vault. It does not move old funds or enable a Flap market.

The WS rollout replaced the obsolete v3 **testnet configuration** with a freshly verified v4 market and vault. Previous standard deployments are retained in `contracts/deployments/bnb-testnet-pre-ws-v4.json` and `contracts/deployments/bnb-testnet-ws-v4.json`; the active `bnb-testnet.json` may point to the separate mock deployment for browser testing; the old local deployment journal and manifest are archived under ignored `backend/data/testnet/history/pre-ws-v4/`. Old contracts, balances and PG rows are retained; this is not an asset migration.

### Real Claude verification with repeatable UUIDs (isolated test only)

`RepeatUuidMockTestDeployment` is a separate chain-97/local-only deployment. It retains the actual provider account record and UUID, but accepts independently signed attempt IDs. Each new verification creates a different attempt ID, allowing the same verified UUID to mint another NFT without overwriting old reservations or receipts. The same attempt/signature cannot mint twice; all ordinary production contracts continue binding nullifiers to the UUID and rejecting duplicates.

Deploy into a separate private directory with `ONHOLD_TESTNET_DATA_DIR=backend/data/testnet-v4-repeat npm run deploy:testnet -- --mock --repeat-uuid`, without `--activate`. Start it with `ONHOLD_TESTNET_DATA_DIR=backend/data/testnet-v4-repeat node backend/scripts/start-testnet.mjs --e2e --real-standing --repeat-uuid`. The local wallet bridge selects this isolated market without editing the public/frontend deployment configuration. The browser banner states **Real Claude verification / Repeat UUID enabled / Mock swap pricing**. Enter the real sessionKey only in the local form; it is sent to the fixed Claude standing endpoint and discarded. This mode disables the synthetic standing endpoint. Real account eligibility, wallet consent/signature, immutable metadata and real testnet minting remain required; real account details become permanently public on the test chain upon minting.

The debug API requires both `MOCK_ONLY()` and `UUID_UNIQUENESS_DISABLED()` on chain 97 before accepting the repeat-UUID flag. Release builds reject this test override. Repeated UUID NFTs are for testing and must not be treated as unique-account compensation claims. The original E2E report remains evidence for the original Mock deployment, not for this new real-account flow; that requires an actual user-supplied valid session and a successful provider response.

When the original runtime is already running, keep it intact and use separate loopback ports: `ONHOLD_TESTNET_PORT=4192 ONHOLD_E2E_PORT=4199 ONHOLD_TESTNET_DATA_DIR=backend/data/testnet-v4-repeat node backend/scripts/start-testnet.mjs --e2e --real-standing --repeat-uuid`. The real-account test page is then `http://127.0.0.1:4199/claim`. Custom E2E ports currently support real-standing mode only.


Mining network statistics use confirmed PostgreSQL projections, without RPC calls per page request. Rust samples network weight and exact per-weight daily emission every 15 minutes, persists real observations in `mining_samples`, and caches the latest sample plus 1H/4H/1D/7D/30D/90D series in Redis (`onhold:mining-stats:v1:<market>`, 30-minute TTL). Longer windows retain the latest real sample per hour/4 hours/12 hours to bound chart size. Missing history is never fabricated. Stale indexing postpones sampling; failed Redis reads fall back to the last memory snapshot with its original timestamp. Wallet weight and share continue to use the same recent confirmed block. These statistics describe weighted NFT reward competition, not PoW hash work or Bitcoin difficulty.

## SingleSpark wallet integration

The wallet controls reuse SingleSpark components and the vendored EIP-6963/EIP-1193 runtime under `front/components/singlespark/runtime/` (source and adaptations recorded there). Users choose their installed MetaMask, OKX, Binance, Coinbase or legacy browser wallet. First connection requests account access and a separate, explicit user signature permanently fixing the invitation source (including no inviter). Existing bindings restore without signing again; NFT minting still requests its existing authorization signature. All ethers mint, bid, staking and recovery paths use that selected provider, and account changes or logout invalidate subsequent signing. No SingleSpark backend login or cross-chain launch configuration is imported.

An unsupported wallet network is shown with an explicit BNB Testnet switch action. Only unknown-chain error 4902 may add the pinned chain-97 profile, followed by a switch and chain check. Remembered connections restore with `eth_accounts`, without requesting new authorization. Disconnect clears the site's selected provider and prevents silent reconnection; extension-level permissions must be revoked inside the wallet if desired. WalletConnect QR sessions are not implemented.

Invitation URLs supply `?ref=<12-character code>` automatically. Navigation preserves the source until connecting. The backend issues a ten-minute, single-use challenge scoped to site, chain 97, market, wallet and inviter. After wallet signature verification it inserts an immutable record in `wallet_referrals` within the existing persisted `/data/events.sqlite3`; `referral_challenges` stores temporary nonces. Existing NFT or chain bindings take precedence. Opening your own invitation link falls back to a signed no-inviter binding instead of blocking wallet connection; other invitation errors remain explicit. Mint authorization requires the saved relationship and rejects a changed code. Claim displays the saved link read-only; changing a URL cannot overwrite an established binding. The existing contract fixes the same relationship at first mint/stake; connection itself sends no chain transaction.

Free NFT 的权重为 0，可铸造、质押和解押，但不产生挖矿或邀请收益；Pro／Max 权重仍为 1／3。新测试网合约部署后，旧合约及其 NFT、质押、奖励和广告记录保留在原地址，不自动迁移。铸造记录按市场合约地址隔离，邀请码保持钱包固定。

## Split NFT and gameplay test deployment

`OnholdNFT` is the permanent ERC721 identity: mint proof verification, immutable records/artwork, Free/Pro/Max weights and one-time wallet referral binding. It deploys without an ERC20 or a Vault. `OnholdGameplayVault` is a separate ERC1967/UUPS instance that holds staking/reward/ad accounting. Its initializer fixes the NFT and 18-decimal reward-token addresses; there are no asset replacement setters. Its implementation is locked and proxy initialization is atomic. Only its owner can upgrade gameplay. Upgrades still require storage checks and review; owner-only access does not protect users from a malicious authorized upgrade. Production requires a multisig/timelock owner.

`contracts/scripts/deploy-split-testnet.mjs` defaults to read-only preparation. `--send --nft-only` deploys only the independent NFT; omit `--nft-only` to additionally create an isolated test-only token, Mock swap route and funded gameplay Vault. ### Flap built-in burn event indexing

The existing buyback vault is already indexed through the shared WebSocket log stream, with three-block confirmation, PostgreSQL deduplication, disconnect backfill and reorg replay. To index Flap built-in deflation instead, configure `ONHOLD_FLAP_BURN_TOKEN` and `ONHOLD_BUYBACK_FROM_BLOCK` (the token creation block), and remove `ONHOLD_BUYBACK_VAULT`; the two sources are mutually exclusive. `ONHOLD_BUYBACK_TOKEN_SYMBOL` controls the displayed unit. Only 18-decimal tokens bound to their processor are accepted. The token address keys the separate checkpoint, preserving the old vault's history.

The active BNB testnet launch uses `contracts/flap-tax-policy.json`: 3% buy / 3% sell, with distributable tax split 50% to native deflation and 50% to LP. Token `0xF98926D4f930a2345eA55D496e3214D37Bf17777` and its official processor are recorded in `contracts/deployments/flap-native-testnet-20261022.json`. The API reads their tax rates and allocations at its confirmed checkpoint. The old tax-buyback keeper is stopped; the separate advertising keeper remains running. NFT, mining-token and gameplay-vault addresses are retained.

The initial buy allocated 0.00054 test BNB each to deflation and LP. A permissionless official `dispatch()` succeeded without burning because the deflation bucket was below its current trigger threshold; zero burns and an empty history are the real chain state. No LP has been added because the token has not migrated to a DEX. Official bot automation and post-migration LP execution on the public testnet are not yet verified. The old vault checkpoint and history remain stored separately.

For a zero-public-BNB integration check, run `npm run test:flap-fork` with Anvil installed and access to the BNB testnet RPC. This starts a loopback-only fork at block 138191965, uses the deployed Flap contracts, and funds an impersonated wallet only inside Anvil. The canonical records are ERC-20 `Transfer` logs from the bound TaxProcessor or token contract into its Flap black hole, the dead address or zero address. User transfers are excluded. `TokensBurned` is not added a second time. Direct burns expose `spent` and `gas_refunded` as null; the UI hides the unrelated keeper threshold and schedule. A token that allocates zero tax to built-in deflation will have no such protocol records. Bonding-curve buyback expenditure is not reconstructed by this adapter; add verified processor swap-event decoding before displaying that amount.

The API currently has a single PostgreSQL index cursor per contract. Avoid overlapping old/new API indexers during a release: stop only the API component, wait for its old pods to exit, then start the new version. Keep PostgreSQL, Redis and keeper workers running. A one-replica rolling update can still create two API pods temporarily.
